## 一、802.11 基础

### 1.1 帧的三种类型

| type | 名称 | 本项目关心什么 |
| --- | --- | --- |
| 0 | 管理帧（Management） | beacon / probe / deauth——扫描、泛洪、踢人全靠它 |
| 1 | 控制帧（Control） | RTS / CTS / BlockAck / PS-Poll：只用来**判断"有客户端在活动"** |
| 2 | 数据帧（Data） | 客户端→AP 的加密数据：能读出 Addr1/2/3，用来找被踢对象 |

帧头（管理帧）24 字节，都是空口字节序：

| 偏移 | 字段 | 长度 | 说明 |
| --- | --- | --- | --- |
| 0 | Frame Control | 2 | 协议版本(2b) + type(2b) + subtype(4b) + flags |
| 2 | Duration | 2 | 通常 0 |
| 4 | Addr1 | 6 | 接收方（dest） |
| 10 | Addr2 | 6 | 发送方（src） |
| 16 | Addr3 | 6 | 对管理/数据帧通常是 BSSID |
| 22 | Sequence Control | 2 | fragment(4b) + seq(12b) |
| 24 | 载荷 | — | 管理帧是固定字段 + IE（SSID、速率、加密…） |

### 1.2 本项目用到的管理帧

| 子类型 | 名称 | 谁发 | 用途 |
| --- | --- | --- | --- |
| 4 | Probe Request | 客户端 | "周围有哪些网？"（可带 SSID，不带就是广播探测） |
| 5 | Probe Response | AP | 回应探测，携带 SSID/速率/加密 |
| 8 | Beacon | AP | 约每 100 ms 广播一次，作用同 Probe Response |
| 12 | Deauthentication | AP 或客户端 | "断开"，reason code 说明原因 |

deauth 帧载荷只有 2 字节 reason code：

```
reason 1 = Unspecified                 reason 4 = Inactivity
reason 2 = Previous auth invalid       reason 7 = Class-3 frame from nonassociated station
reason 3 = Deauth leaving              reason 15 = 4-way handshake timeout
```

### 1.3 为什么 deauth 有效

客户端与 AP 的关联是个状态机（未认证 → 已认证 → 已关联）。deauth 是"已认证/已关联"状态下的
合法管理帧，**接收方不做任何来源认证**：只要帧的 BSSID/SA 看着像自己的 AP，就照做——断开、
清空会话密钥、重新扫描重连。而且因为 deauth 是**未加密的管理帧**，任何能发 802.11 帧的设备都能伪造。

这既是它有效的原因，也是它必须只用于自有网络的原因。

### 1.4 信道、频段、国家码

- 2.4 GHz：信道 1–13（1–11 全球通用，12–13 部分国家）。
- 5 GHz：36/40/44/48、52–64、100–144、149–165，不同国家可用集合不同。
- `esp_wifi_set_channel()` 会按**当前国家码**校验信道；越界直接返回 258，攻击"看起来发了但没效果"。
  所以本项目按目标信道临时设国家码（见 §2.4）。
- 射频只有一个，跳信道意味着**离开原信道就收不到原信道的帧**——多 AP 模式必须轮流跳。

### 1.5 速率与"11n 收不到 Wi-Fi 6"

| 代际 | PHY | 前导/编码 |
| --- | --- | --- |
| 802.11b/g | DSSS/ERP-OFDM | 1–54 Mbps legacy |
| 802.11n（HT） | OFDM + MIMO | ESP32 支持 |
| 802.11ac（VHT） | 5G only | 不支持 |
| 802.11ax（HE） | OFDMA | **不支持** |

ESP32 是 11n 设备：对 HE PPDU 既不能解析、也不会当成 legacy 帧交给上层。
所以当目标 AP 下只有 Wi-Fi 6 客户端时，抓包只看到 beacon/probe response/广播数据，
没有 client→AP 帧 → 嗅探触发条件不成立 → `rxm` 不增长。这是**射频能力限制**，不是逻辑 bug。
现在的处理是加一层**盲发兜底**：每 500 ms 给当前 AP 发一帧广播 deauth（`blind=` 计数），
即便一个客户端帧都解不出来，攻击也仍有动作；帧上空气与否由 `txok` 和第二块板的 `RXMIX deauth=` 证明。

## 二、六种攻击的原理与本项目实现

### 2.1 Deauth：嗅探触发，而不是盲发

盲发（对着某个 BSSID 无脑发广播 deauth）有两个问题：不知道被踢客户端的 MAC（很多客户端会忽略
广播 deauth），也不知道现在有没有人在通信（空放浪费、更容易被发现）。

本项目改成"监听 → 命中 → 回敬"：

```c
esp_wifi_set_promiscuous(true);
esp_wifi_set_promiscuous_filter(&filt);   // MGMT | DATA | CTRL
esp_wifi_set_promiscuous_rx_cb(&sniffer); // 在 Wi-Fi 任务里跑
```

`sniffer()` 对每个抓到的帧按三条规则判断：

| # | 判据 | 取谁当被踢客户端 | 说明 |
| --- | --- | --- | --- |
| 1 | `dest == 目标 BSSID` | `src` | 客户端正在发往目标 AP |
| 2 | `bssid == 目标` 且 `dest` 单播 | `dest` | AP 正在发给某个客户端（管理帧） |
| 3 | 控制帧，`dest` 或 `bssid` 命中目标 | 对端 MAC | RTS/BlockAck/PS-Poll 极短，先按 `sig_len` 保护再读地址 |

**reason code 有两种模式**：固定值（1–65535，标准明确定义的是 1–11、13–24）或 `random`
（每束从这 23 个标准值里重掷一个）。非标准值也能发，但客户端很可能直接丢帧，所以 `random`
只在"有定义"的集合里取值。非法输入（0、负数、越界、非数字）会被拒绝，不再静默退化成 reason 1。

命中后发 **3 帧，两个方向都伪造**：

| 帧 | Addr1 (dest) | Addr2 (src) | Addr3 (BSSID) | 效果 |
| --- | --- | --- | --- | --- |
| AP→STA 单播 | 客户端 | 目标 AP | 目标 AP | 客户端认为"AP 把我踢了" |
| STA→AP 单播 | 目标 AP | 客户端 | 目标 AP | AP 认为"客户端要走了"，拆关联并通常自己再通知客户端 |
| 广播 | `FF:FF:FF:FF:FF:FF` | 目标 AP | 目标 AP | 只认广播 deauth 的设备 |

两个方向都发的原因很直接：只伪造 AP→STA 时，那些"校验 deauth 必须来自自己 AP"的客户端会满足条件，
但反过来只伪造 STA→AP 会被 AP 的 PMF/严格实现拦下；两条路一起走，命中率明显更高。
（PMF 开启时两个方向都会被签名校验拦掉，这是协议设计的目的，注入绕不过去。）

帧数用 `NUM_FRAMES_PER_DEAUTH` / `NUM_REVERSE_PER_DEAUTH` / `NUM_BROADCAST_PER_DEAUTH` 控制，默认 1/1/1：
单播帧要等 ACK，一次发多了会撞满 TX 缓冲。
`deauth_frames`、`txok`、该 AP 的 `frames` 同步加，`eliminated++`（命中轮数）。

**为什么不是一次发 16 帧。** 早期版本在混杂回调里连发 16 帧单播，`deauth_frames` 涨得挺欢，
实际大半帧没出去：单播管理帧要等 ACK，对方不回就一直占着 TX 缓冲，很快 `esp_wifi_80211_tx()`
开始返回 `ESP_ERR_NO_MEM(257)`，而返回值被忽略了。现在：

- 回调**只入队**（"该踢谁"，16 深），发包交给主循环；
- 主循环 1 ms 出队一次、一帧一帧推，推不动就退避 5 ms 重试（帧不丢，只是慢一点）；
- `STATUS` 的 `txok / txerr / txerr_nomem / txec / txdrop` 把这件事变成可观测的。

**盲发兜底。** 嗅探触发有个硬前提：得先看见该 BSS 的上行流量。客户端完全静默、或者只跑
802.11ax（11n 解不出来）时永远触发不了，所以每 500 ms 额外给当前 AP 发一帧广播 deauth
（`BLIND_DEAUTH_PERIOD_MS`，`blind=` 计数）。广播帧不需要 ACK，代价极低。

四种目标模式共用这套判据，只改"目标集合"和"信道轮询"：

| 模式 | 命令 | 目标集合 | 信道 |
| --- | --- | --- | --- |
| SINGLE | `DEAUTH <idx>` | 1 个 AP | 固定 |
| ALL | `DEAUTH_ALL` | 扫描到的全部 AP | 每 250 ms 跳下一个 |
| ONLY | `DEAUTH_ONLY i,j` | 白名单 | 只在名单内轮 |
| EXCEPT | `DEAUTH_EXCEPT i,j` | 全部 − 名单 | 跳过名单 |

### 2.2 Raw frame 注入与 sanity check 绕过

`esp_wifi_80211_tx()` 会检查帧的合法性，伪造的 deauth 会被判非法（`ESP_ERR_INVALID_ARG`）。
绕过办法是在应用层覆盖 Wi-Fi 私有库里的检查函数：

```c
extern "C" int ieee80211_raw_frame_sanity_check(int32_t a, int32_t b, int32_t c) {
  return 0;   // 0 = 通过
}
```

该符号在 `libnet80211.a` 里也存在，所以链接必须允许重复定义：
`CMakeLists.txt` 里 `-Wl,-z,muldefs`。ESP32-C5 的库同样导出该符号，手法不变。

### 2.3 Probe / Beacon 泛洪

构造大量"看起来正常"的伪造 AP：

- 子类型 **8（Beacon）** 与 **5（Probe Response）** 交替发送（每轮 4 帧、4 ms 一发）；
- SSID 随机（`rand_ssid()`）、BSSID 每帧随机；
- 用 **1 Mbps legacy 速率**，任何客户端都解得动；
- 每 120 ms 换信道，覆盖 1–13（C5 上还覆盖 5 GHz）。

效果是让附近设备的"可用网络列表"被假 AP 填满（名称杂乱、无法连接），属于干扰类效果，
不会把某个客户端踢下线。**本项目只保留这一种 Probe 泛洪**：早期"针对指定 STA 的定向 probe"
已被删掉（用户需求变更）。

帧计数：`probe_frames` 每发一帧 +1（`STATUS` / `STATS` 都能看到）。

### 2.4 信道 / 国家码 / 双频

| 目标信道 | 国家码 | 掩码 |
| --- | --- | --- |
| 1–11 | `01` | 默认（1–11） |
| 12–13 | `CN` | 1–13 |
| ≥ 15（5 GHz） | `CN` | 显式 5G 掩码（36…165） |

C5 额外 `esp_wifi_set_band_mode(WIFI_BAND_MODE_AUTO)`，之后设信道时射频自己选频段。
**双频不需要两套 sdkconfig**：频段是运行时按目标信道切的。

扫描时用"全信道 + 5G 掩码"配置，否则 12/13 与 5G 的 AP 不会出现在结果里。

### 2.5 CSA 欺骗（Channel Switch Announcement）

PMF 让 deauth 失效之后，CSA 是最直接的替代路线：CSA 走的是 Beacon/Probe Response 的 IE 或
Action 帧，**不属于 robust 管理帧，802.11w 不校验它**。

两种播报形式，本项目都用：

| 形式 | 结构 |
| --- | --- |
| CSA IE | `ID=37` `Len=3` `Mode` `NewChannel` `Count`（挂在 Beacon / Probe Response 里） |
| Action 帧 | `Category=4`（Spectrum Management）`Action=4` + `Mode` `NewChannel` `Count`，共 29 字节 |

伪装的要点（也是与"随手发一帧"的区别）：

1. **Count 要像真 AP**：连续发 `5→4→3→2→1`，每 100 ms 一轮，客户端在 count 归零时切信道；
   单发 `count=1` 很容易被 WIDS 判为异常。
2. **广播 + 单播都要**：广播覆盖面大，但部分驱动只认单播；实测比例约 3:1。
3. **新信道要"接应"**：countdown 结束后跳到新信道，每 100 ms 发一个克隆 beacon
   （同 BSSID/SSID，RSN IE 从真 AP 的 beacon 里抄），否则客户端一两秒就回扫原信道。
4. **别配 deauth**：PMF 下 deauth 会被丢并触发 SA Query，反而暴露；只靠 CSA 就够。

**新信道上的"假 AP"**：把客户端骗到新信道之后，只发 beacon 是不够的——客户端一看没有 AP
就回扫原信道。所以每轮在新信道停留 500 ms，冒充那个 AP：**Auth 回成功**（algorithm 0 / seq 2 /
status 0），**Assoc/Reassoc 回失败**（status 17，AP 无法再接客户端）。客户端于是进入了
"认证通过、关联被拒、继续重试"的循环，留在新信道上。这一段不需要任何爆破素材，纯干扰。

实现（`src/csa.cpp`）：`CSA <idx>` 走自动模式 —— **2.4G 的 AP 通告一个随机 5G 信道，5G 的 AP 反之**，
每轮重新随机，状态机 `announce → hold → announce …` 一直循环到 `CSASTOP`（`csaauto=1` / `csacycle=`
可观测）。也可以 `CSA <idx> <ch> [cnt] [secs]` 指定信道做单次播报。
`STATUS` 的 `csa=/csaf=/csac=/csch=` 可观测，`CSATEST` 打印原始字节，`MON <ch> <secs>`
让第二块板固定信道抓包（`RXMIX` 里 `csa_action` / `csa_ie` 单独计数）。

### 2.6 DELBA 欺骗（拆除 Block Ack 会话）

前三节打的是"让客户端连不上"。DELBA 打的是"让它连着但很慢"。

**Block Ack 是什么。** 802.11n 起，高吞吐靠 A-MPDU 聚合：发送方在一个聚合里塞多帧，
接收方用一张位图统一确认。这个会话按 TID（0–7，QoS 优先级）单独协商：ADDBA Request/Response
建立，DELBA（Category 3 / Action 2）拆除。会话一拆，聚合就没了，链路退回"一帧一确认"。

**为什么可伪造。** DELBA 属于 Block Ack 类，**不在 802.11w（PMF）的 robust 管理帧名单里**，
所以 WPA3 客户端也照收；接收端只按 TA 找"这是不是我的 AP"，不校验任何密码学凭证。

帧结构（30 字节，本项目 `src/delba.cpp`）：

| 字段 | 值 |
| --- | --- |
| Frame Control | `D0 00`（管理帧，subtype 13 = Action） |
| Addr1 / Addr2 / Addr3 | 受害者客户端 / 目标 AP 的 BSSID / 目标 AP 的 BSSID |
| Category | `3`（Block Ack） |
| Action | `2`（DELBA） |
| DELBA Parameter Set | `bit11 = Initiator`、`bit12-15 = TID`（本工程置 Initiator=1，冒充"AP 要停聚合"） |
| Reason Code | 默认 `37`（"对端不再想用这个机制"），也可选 1/32/38/39 |

**盲发没用。** 对没有该 TID 会话的客户端发 DELBA，mac80211 直接丢。所以分工是：

1. **先听**：从 QoS 数据帧的 QoS Control 认 TID；从 BA/BAR 控制帧的 BA Control（bit2-5）认 TID；
   从 ADDBA Request/Response 认 TID（能收到的话）。同时按 Addr2/Addr3 学客户端 MAC。
2. **再发**：对每个已知客户端，按它实际用过的 TID 单播 DELBA，**两个方向都伪造**——
   AP→STA（Addr2=AP，客户端以为是 AP 拆的）和 STA→AP（Addr2=客户端，让 AP 自己拆它的发送会话）。
   一个方向拆掉就够了，因为聚合必须两侧状态都在。
3. **兜底**：一个客户端 MAC 都没听到时，发**广播 DELBA**（Addr1=FF..FF，TA=AP）。多数驱动对
   广播 DELBA 也按 TA 找会话，所以仍有杀伤；`STATUS` 的 `delbb=` 单独计数。
4. **保持**：每 100 ms 对每个客户端按观察到的 TID 重发一轮（`delbt` 位图），
   客户端重建议程（再发 ADDBA）会被再拆一次，链路一直"连着但很慢"。

实测（本实验室拓扑，攻击板 ESP32-CYD / AP 板 ESP32 / 客户端 ESP32-C5，5 GHz 不参与）：

| 阶段 | 客户端下载速率 |
| --- | --- |
| 攻击前 | 480–630 KiB/s（约 4–5 Mbit/s） |
| 只发广播 DELBA（还没学到客户端 MAC） | 0–260 KiB/s，约 **-75%** |
| 学到客户端后按 TID 单播（双方向） | 0–5 KiB/s，约 **-99%** |
| 停止攻击后 | 逐步恢复 |

客户端全程**没有掉线**（没有去认证/去关联，TCP 也没断，只是慢）：这正是 DELBA 的隐蔽之处。
第二块板（C5）在攻击信道被动监听时，`RXMIX` 报 `action=84 delba=82 addba=0`，说明帧确实上了空口。

**嗅探能力（实测，别再猜）**：把一块板切到 `MON`，在监控窗口内让客户端重新关联一次：

```
RXMIX beacon=953 proberesp=71 probereq=23 deauth=1 auth=2 assoc=1
      other_mgmt=7 ctrl=0 data=13628 action=7 addba=7 delba=0
```

- **单播管理帧收得到**：`auth` / `assoc` / `action(addba)` 都在，所以“听到 ADDBA 立刻补刀”这条路
  真的会触发——同一轮攻击里 `delbab=7`、`delbtr=5`、`delbat=0xA1`（正好是 C5 协商的 TID 0/5/7）。
- **控制帧要开两级过滤才收得到**（这是本工程踩过的坑，已修）：`esp_wifi_set_promiscuous_filter()`
  的 mask 只决定"控制帧这一大类要不要"，真正决定哪些控制 subtype 上报的是
  `esp_wifi_set_promiscuous_ctrl_filter()`，而**它的默认值把所有控制帧全丢掉**（读回 `0`）。
  实测（同一块板、同一个信道、另一块板注入 10 帧 RTS）：

  | 二级过滤 mask | 结果 |
  | --- | --- |
  | `0`（默认） | `ctrl=0 rts=0 ack=0` —— 一帧都收不到 |
  | `WIFI_PROMIS_CTRL_FILTER_MASK_ALL`（0xFF800000） | `ctrl=37 rts=10 ba=2 bar=1 ack=24` |

  其中 `rts=10` 正好是注入的 10 帧。所以"MON 能看到一切"这句只有在两级过滤都开了之后才成立；
  本工程的 `start_promiscuous()` 现在会显式设 `MASK_ALL`，顺带让 deauth 的
  "控制帧触发"（RTS/PS-Poll 找客户端）第一次真正生效。
- 结论：TID 有两条可用来源（ADDBA 精确触发 + QoS 数据帧周期扫描），第三条（BA/BAR）在本硬件上不可用。

### 2.7 BA 会话劫持（DELBA → 伪造 ADDBA → BAR）

DELBA 只负责"拆"，拆完的对端会自己重建。这条链要的是**由我们决定会话参数**：

```
1) 伪造 DELBA        清场：让对端先把旧会话丢掉，我们的 ADDBA 才不会被当成重复会话拒绝
2) 伪造 ADDBA Request 种窗口：接收端用请求里的 SSN 初始化 WinStartB（802.11-2020 10.25.6.6）
3) 伪造 BAR           推窗口：把 WinStartB 一直顶在真实 SN 前面
```

三个帧的结构（本工程 `src/delba.cpp`，`BATEST` 可打印原始字节）：

| 帧 | 长度 | 关键字段 |
| --- | --- | --- |
| ADDBA Request | 33 | `cat=3 act=0`，dialog token，参数集（bit2-5=TID、bit6-15=buffer size），timeout，**SSN<<4** |
| BAR（压缩） | 20 | 控制帧 subtype 8，BAR Control（bit2=压缩、bit4-7=TID），BAR Info = **SSN<<4** |
| DELBA | 30 | `cat=3 act=2`，参数集 bit11=Initiator、bit12-15=TID，reason |

两个方向都伪造：`SA=AP → STA`（动客户端的接收窗口）、`SA=STA → AP`（动 AP 的接收窗口）。
窗口只有 64 帧而 SN 空间 4096，所以只要把 SSN 顶到真实流前面几十帧，后续合法帧就全被判成"旧帧"丢掉。

**为什么窗口大小可能变得很小**：真正的 WinSizeB 由接收端在 ADDBA Response 里声明，攻击者在
Request 里填小 buffer size 只是"建议"；实现若镜像了该值，窗口就从 64 缩到个位数，错位一点点
就够永久队头阻塞。

#### 实验室实测（ESP32 当 AP、C5 当 STA、CYD 攻击，ch1，TCP 下载）

| 条件 | 攻击前 | "种窗口"后（**已停止注入，纯静默**） | 停手 8 s 后 |
| --- | --- | --- | --- |
| `BAPLANT step=512`（把窗口顶到 SN 前 512） | 386 KiB/s | **26–30 KiB/s** | 0 KiB/s |
| `BAPLANT step=0`（对照：SSN 不动窗口） | 404 KiB/s | **43 / 8 KiB/s** | 0 KiB/s |
| `BAATTACK`（DELBA+ADDBA+BAR 持续） | 302 KiB/s | 22–26 KiB/s | 67 KiB/s |
| `BARPUSH step=512`（**只发 BAR**，不发 ADDBA/DELBA） | 304 KiB/s | 12 KiB/s | 3–16 KiB/s |
| `BARPUSH step=0`（同上，SSN 不推窗口） | 340 KiB/s | 0–3 KiB/s | 0 KiB/s |

**Android 客户端上的判定实验**（用户操作，手机连自家 AP 播放视频，攻击板只发 BAR 后静默）：

| 条件 | 现象 |
| --- | --- |
| `BARPUSH <idx> 512` | 视频卡死，手机**仍显示已连接**，Wi-Fi 关开后才恢复 |
| `BARPUSH <idx> 0`（对照） | 视频照常播放，无影响 |

`step=512` 与 `step=0` 的差别只有 SSN——两者都只发了 BAR、发完即静默。所以这一次是
**WinStartB 真的被推到了真实序列号前面**，Bl0ck 的"推窗"那一步在 Android 客户端上成立。
（证据强度：用户现场观察、单设备单次、无抓包；记录为"人工确认"。）

结论要写清楚，别把功劳算错：

1. **只发 2 帧伪造 ADDBA 就能把一条 4 Mbit/s 的流打死，而且停手后不恢复**——必须重新关联
   （重启 AP 或让客户端重连）才回到 380 KiB/s 以上。这与"客户端不断连但 QoS 数据冻结"的现象一致。
2. **但 SSN 的值不是主因**：`step=0`（窗口根本没被推走）同样打死。也就是说在这对
   ESP-IDF AP/STA 上，起作用的是**BA 会话状态被第三方改写**（session hijack / 协商被压制），
   而不是"WinStartB 被推到真实 SN 前面"这个窗口技巧本身。
3. 为了把"推窗"和"会话状态被改写"分开，又做了 `BARPUSH`：**只发 BAR**（不发 ADDBA/DELBA）。
   在 ESP-IDF 目标上（ESP32 AP / C5 STA）`step=512` 与 `step=0` 都能把链路打死（12 KiB/s 与
   0–3 KiB/s）——它们**任何伪造的 BA 类帧都会破坏会话**，所以这对设备上分不出窗口那一步。
4. 换成 Android 客户端后差别就出来了：`step=512` 卡死、`step=0` 无影响。
   即 **Bl0ck 的"推窗"机制在 Android 客户端上成立**；ESP-IDF 那对设备属于"更容易被打死，
   但打死的原因不是推窗"。两件事分开记，别混成一句"BA 攻击有效"。

#### 边界

- 只影响 QoS Data（管理帧、非 QoS 数据不受影响），TID 会话有 inactivity timeout。
- 注入本身会把驱动 TX 队列打满：实测 15 s 内 `baerr=1559`，所以代码里做了每轮 4 帧的上限 +
  失败退避 5 ms，否则大部分帧根本发不出去（`esp_wifi_80211_tx` 返回 `ESP_ERR_NO_MEM`）。
- `BAATTACK` / `BAPLANT` 的 `step` 取 0–2047；`<128` 是对照条件（SSN 仍在当前窗口内）。

### 2.8 Evil Twin 钓鱼链路

```
1) SCAN 选目标网络
2) 用同名（开放）SSID 起一个克隆 AP，同时向真 AP 的客户端发 deauth（约 3 s）
3) 客户端掉线 → 看到同名热点 → 手动/自动连上克隆 AP，拿到 192.168.4.x
4) 内置 DNS 把任意域名解析到 192.168.4.1 → 浏览器弹"需要认证"
5) GET / 渲染带目标 SSID 的登录页；POST /login 收 username/password 入表（RAM，上限 50 条）
   然后回"密码错误"让人重试
6) CREDS 把表导出到串口
```

**真实效果限制**：克隆 AP 是开放式，已保存 WPA2 密码的设备通常不会自动去连同名开放热点；
成功率依赖用户手动连接。真 AP 若启用 802.11w/PMF，deauth 会被直接丢弃。
本工程对这条链路只做到"命令能接上"，全链路未实测（见测试报告）。

## 三、代码框架

### 3.1 数据流

```
                ┌──────────────── serial_console.cpp ────────────────┐
串口字节 ──► 行缓冲 ──► dispatch()  ──►  do_scan / do_deauth / do_probe_broadcast
                ▲                          do_stations / do_stats / do_evil_twin
                │                          │
                │                          ▼
                │                    deauth.cpp / evil_twin.cpp / general.cpp
                │                          │
                │                          ▼
                └── ui_log() ◄──────  计数器 + 状态（g_scan_*、deauth_frames…）
                                             ▲
LVGL 按钮 ──► 命令队列 ──► wireless_console_execute() ──┘
```

要点：

- 命令只有一条执行路径（`dispatch`），屏上按钮走 `wireless_console_execute()` 进来，与串口完全等价。
- 攻击函数只更新计数器与状态，**不直接打印**；打印集中在 console 层，避免协议流被中间层污染。
- 扫描是独立任务（`scan_task`），结果通过 `g_scan_*` 缓存给后续 `DEAUTH` 用。

### 3.2 关键数据结构

`include/types.h` 里的帧结构体按空口顺序排布，直接强转后填地址即可发送：

```c
typedef struct {
  uint16_t frame_control;   // 0x00C0 => type 0 / subtype 12 (deauth)
  uint16_t duration;
  uint8_t  dest[6];         // Addr1
  uint8_t  source[6];       // Addr2
  uint8_t  bssid[6];        // Addr3
  uint16_t seq;             // 0xF0FF（fragment 0 / seq 4095）
  uint16_t reason;
} deauth_frame_t;
```

AP 表（`ap_info[]`）记录：BSSID、SSID、信道、enabled 标志、已发帧数。
`SCAN` 填充它，`DEAUTH_ONLY/EXCEPT` 只改 `enabled`，攻击循环按表轮询。

### 3.3 状态机与计数

| 变量 | 语义 |
| --- | --- |
| `attack_mode` | `idle` / `single` / `all` / `only` / `except` / `eviltwin` |
| `deauth_frames` | 累计 deauth 帧数（每命中 +16） |
| `probe_frames` | 累计泛洪帧数（每帧 +1） |
| `eliminated_stations` | 命中轮数 |
| `ap_info[i].frames` | 该 AP 已发帧数（`STATS` 输出） |
| `rx_frames` / `rx_matched` | 监听到的帧数 / 命中判据的帧数（诊断 `d=` 为什么不涨） |

### 3.4 LVGL 界面的解耦方式

界面全部在 `components/wireless_ui/`，主固件只 include 纯 C 的 `wireless_ui.h`：

| 方向 | 机制 |
| --- | --- |
| UI → 固件 | `wireless_ui_set_command_cb()` 注入回调，按钮只发协议行 |
| 固件 → UI | `wireless_ui_scan_begin/add_network/scan_end/status/log()` 置标志 |
| UI 需要存储 | app 注入 `wireless_ui_storage_ops_t{load,save,clear}`（NVS 由 `src/storage.cpp` 实现） |
| 编译期 | `CONFIG_WIRELESS_ATTACK_LVGL_SUPPORT` + 组件 `CMakeLists` 里整体打包/整体为空 |

这样做的原因：该 IDF 版本下组件 `REQUIRES nvs_flash` 不会把 include 路径传给依赖方，
干脆依赖倒置，让组件不认识 NVS。

实现细节：

- 点行只 `lv_label_set_text()` 刷新那一行，**不重建列表**——在自己的回调里删除事件对象容易踩坑。
- 进弹窗时快照 `s_picked / s_selected`，`Back` 还原，`OK` 保留。

### 3.6 触摸与校准

- XPT2046 走独立 SPI（MOSI 32 / MISO 39 / SCLK 25 / CS 33），有互斥锁保护。
- **PENIRQ（GPIO36）该板未接**，判"按下"只能靠原始值窗口 `120…3975`。
- 校准：800 ms 静置后连续 3 次采样稳定（±80）才记录，记录后锁存到松手，避免抖动/重复触发。
- 解算：

```
axis_x = 原始轴里在屏幕 X 方向变化更大的那个
gain_x = (屏宽 - 1 - 2*inset) / (右边缘均值 - 左边缘均值)    // 可为负
screen_x = inset + (raw[axis_x] - offset_x) * gain_x
```

结果存 NVS（命名空间 `wui`，键 `calib`）。

### 3.7 内存约束（ESP32 无 PSRAM）

| 项 | 值 | 备注 |
| --- | --- | --- |
| LVGL 堆 | 64 KB | 32 KB 时 30+ 列表行会卡死主循环 |
| 绘制缓冲 | 12.8 KB | 320×20×2，单缓冲 + DMA |
| 列表行 | 30 | 数据仍保留 64 条，超出部分滚动 |
| CJK 字库 | 57 KB | LVGL 内置 191 KB |
| 静态数据 | 约 5 KB | `s_rows[64]` 等 |

## 五、局限（写清楚，别当成 bug 追）

1. **11n 射频解不出 HE**：目标 AP 下只有 Wi-Fi 6 客户端时抓不到 client→AP 帧，`rxm` 不涨
   （现在有 `blind=` 广播兜底，不再"完全没动作"）。
2. **Evil Twin 未全链路验证**：5G 克隆 AP、凭据回传全流程未实测。
3. **单射频**：多 AP 模式必须跳信道，跳走期间原来的信道收不到帧（命中率与信道驻留时间相关）。
4. **UART RX 缓冲**：已从默认 256 B 提到 4 KB（`SERIAL_RX_BUFFER_SIZE`），300 条指令洪泛不再丢行。
5. **C5 没有触摸屏界面**：Kconfig 宏依赖 `IDF_TARGET_ESP32`。
6. **混杂模式必须开两级过滤**（已修，见 §2.6）：只设 `esp_wifi_set_promiscuous_filter()`
   的 CTRL 位不够，`esp_wifi_set_promiscuous_ctrl_filter()` 不设的话控制帧全被丢，`ctrl=0`。
   另外两点常识：注入与接收共用一根天线（半双工，注入密集时丢收包），
   11n 射频也解不出 Wi-Fi 6 的 HE PPDU。
7. **DELBA 依赖"对端在通信"**：没有流量的客户端没有 BA 会话，DELBA 对它无效；静默 BSS 里
   只会看到广播兜底帧（`delbb=`），效果未验证。
8. **BA 会话劫持的窗口机制未单独证明**：实验室里"种窗口"和"不动窗口"都能把流打死，
   分不出是 SSN 起作用还是会话状态被改写；要证窗口那一步，需要 mac80211 之类的目标。
9. **DELBA 不踢人**：链路一直连着，所以现场看起来像"网络很卡"而不是"断了"；这既是隐蔽性
   也是限制——如果目标是让客户端掉线，用 deauth/CSA。
