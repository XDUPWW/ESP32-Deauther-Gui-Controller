# 小米快连弹窗实验结论

记录日期为 2026-11-28。台架使用 Redmi K60（Android 15、HyperOS 3.0、Google Play 服务 26.45.31）、小米手环 10、经典 ESP32 和 Windows BLE 观察端。

## 已观察到的弹窗

| 试验 | 结果 | 证据 |
| --- | --- | --- |
| 未配对的小米手环 10 靠近 K60 | 手机显示「手环 10」系统卡片 | ADB 窗口焦点为 `com.xiaomi.bluetooth/com.android.bluetooth.ble.app.confignet.MiuiConfigNetActivity`，UI 树包含「手环 10」。首次卡片出现在监听开始前 |
| 卡片关闭后尝试再次靠近 | 连续 5 分钟采样 349 次，未见第二张卡片 | 手环仍显示待配对二维码。小米蓝牙组件仍报告收到手环的扫描结果 |
| 对齐小米快连扫描与处理日志 | 控制器反复报告 `ignore the device pop-uo 3 times` | 589 条记录通过地址后缀在本机与手环扫描记录匹配。另一组 437 条日志中，忽略事件与最近一次具名扫描的时间差均在 100 ms 内，中位数为 7 ms |
| ESPP Fast Pair 公开配件端示例在经典 ESP32 上运行 | Windows 收到 84 条匹配示例名称和 Fast Pair 服务标识的广播。K60 在 35 秒内的 40 次采样均未见卡片或相关通知 | ESP-IDF 6.1 构建通过。观察端最强 RSSI 为 −51 dBm。COM5 测试前备份，测试后已恢复并通过 4 MB 整片校验 |
| 体脂秤短时监听 | 51 次窗口采样均未见小米系统配对卡片，Windows 也未收到有体脂秤名称的广播 | 该窗口内缺少可归属于体脂秤的无线样本和受控唤醒时间，体脂秤是否支持系统卡片仍待实测 |

手环卡片已经在 K60 上实测出现，归属小米系统蓝牙组件。日志显示小米快连按已记录的弹窗次数跳过了后续提示。`3` 是日志里报告的计数，计数何时重置、点击「取消」是否会增加计数、它与可见黑名单之间的关系均未确认。首次弹窗之前是否有蓝牙建连或 GATT 交互，也缺少那一时段的手机 HCI 记录。手环状态、手机开关和支持范围见[小米手环 10 官方 FAQ 第 2、14 问](https://www.mi.com/tw/support/faq/details/KA-580855/)。

ESP32 示例验证的是 Google Fast Pair 通道。这一轮确认广播上了空口，手机端的「扫描附近设备」和「包含调试结果」状态尚未核实。Google 的首次发现和后续配对流程见[Fast Pair 认证指南 §3.2](https://developers.google.com/nearby/fast-pair/fast-pair-certification-guideline)。

## MiBeacon 广播的观察结果

| 项目 | 证据与判断 |
| --- | --- |
| 广播类别 | 原记录在手环 10 上观察到一条 18 字节的 BLE 广播数据。可解析出 Flags 和 16 位 Service Data，服务 UUID 为 `0xFE95` |
| 型号与弹窗触发条件 | 现有抓包没有确认小米快连依赖哪些字段，也没有确认观察到的是触发首次发现的广播。把 `0xFE95` 当作扫描分类标记即可 |
| 变化字段 | 两份记录有一个服务数据字节变化。它的语义、是否与状态关联，以及手机是否校验这些数据仍未验证 |
| 早期 ESP32 回放结果 | 研究简报中的两组回放均未收到连接尝试，K60 也未出现通知或弹窗焦点。该结果适用于当时采集的广播和测试状态 |

早期观察和回放结果见[研究简报 §3.4](../../ESP32_Android_Quick_Pair_Research_Prompt.md#34-小米手环-mibeacon回放无效负结果)。其中关于小米通道必然依赖 GATT 或签名的解释应保留为待验证假设，现有证据只够确定两轮回放均未触发。如果报告另存，设备地址和健康数据继续保留在本机。

| +57 ms | `START u0 … MiuiConfigNetActivity` | `ActivityTaskManager` |
| +365 ms | `Displayed … +297 ms` | `ActivityTaskManager` |

- 同一窗口内没有 `BtGatt` 连接、配对或 bond 事件；`dumpsys bluetooth_manager` 也没有该地址的
  绑定记录。**卡片在连接之前出现，广播即可触发。**
- 标题来自 `com.mi.health` 的设备信息（`device name = 小米手环10`），不是帧里带的文本。
- PID 修正：服务数据 `33 58 FA 59 01 …` 的第 2–3 字节是 `FA 59`，小端 **0x59FA**；
  `xiaomi-ble` 1.22.1 的 `DEVICE_TYPES[0x59FA]` 即 Smart Band 10 / M2457B1。
  之前按 `58 FA`（0xFA58）读是错的，差了 1 字节。

## 下一轮复现实验

1. 用处于待配对状态的真手环做阳性实验。K60 保持联网和亮屏解锁，打开小米快连。在手环靠近前启动 Windows 被动 BLE 观察和 ADB 时间戳记录，先记录一段无卡片基线。
2. 卡片出现后暂不点击「连接」。记录卡片可见时间和所属系统组件。在自有测试手机已启用 HCI 调试时，核对该手环的连接事件与卡片出现的先后。重复轮次记录手机是否已显示过同一型号卡片。HCI 日志的可用范围见[Android 蓝牙调试文档](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging)。
3. ESP32 配件端复现可沿用开源的 [ESPP Fast Pair 示例](https://esp-cpp.github.io/espp/ble/gfps_service_example.html)。本次使用 `espp/gfps_service` 1.4.8 和 ESP-IDF 6.1，经典 ESP32 目标编译及链接通过。使用项目公开的开发示例或自有注册型号，分别记录广播、系统卡片和用户点击后配对的结果。
4. 体脂秤复测用待绑定真机。先在 K60 桌面唤醒秤，记录系统卡片。再进入米家 App「添加设备」，对照能否搜到。同一轮应记录确切型号和唤醒时间。S400 的官方流程见[绑定说明](https://www.mi.com/uk/support/faq/details/KA-107891/)。
